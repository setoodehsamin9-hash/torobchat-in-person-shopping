# In-person journey and release design

The user replaces the earlier Torob-style catalog requirement: `/` must redirect to `/chat`; remove the standalone catalog UI, retain product/shop details as auxiliary purchase-flow views. Latest explicit user choice supersedes the working name and compass: use **ترب‌چت — دستیار خرید حضوری**, the locally saved reference GIFs with a static reduced-motion alternative, the reference dark/red palette, and the journey “انتخاب کالا → پیش از حرکت → مسیر مراجعه”. Prioritize locating linked stores and visiting them. Online channels become secondary details. Explicit show_stores/nearby_stores/credit_stores UI actions bypass LLM/embeddings; preserve exact IDs and hard constraints. Free text retains provider orchestration. Route caching is process-local, 120 seconds, at most 128 entries, with coalescing and original calculation timestamps; failures are uncached. Do not debug or change the user's selected LLM as part of this work.

## Neshan
Server-only `NESHAN_API_KEY`; existing interactive OSM preview remains available without credentials. Product photos/titles and only offer-linked stores appear on the map. A request explicitly sends the user's chosen origin to Neshan after a click. Support driving and walking, fastest arrival among up to six selected candidate stores, and a connected multi-stop route for one exact product. All destinations are resolved from valid offer IDs; budget/location/installment filters remain authoritative. Route time/distance are only values returned by Neshan; no straight-line ETA. A nearest-neighbor stop ordering is labeled heuristic, not a globally optimal route. Driving `/v4/direction`; pedestrian documentation is inconsistent between its v4 endpoint and v1 samples, so expose a restricted v1/v4 configuration, default v4. Validate and decode route polylines, bound network/time/response size, and use a persistent daily request cap. No new live key or paid map call is required for implementation verification.

## Asynchronous seller inquiry
Persist owner-scoped quotes, jobs and events. Support voice and SMS through a documented provider-neutral gateway contract, not a claimed working vendor. Live mode is off by default; it requires an operator-managed, verified contact registry independent of the fake dataset numbers, a configured HTTPS gateway, worker credentials, explicit per-job cost approval and daily cost ceilings. No public API can self-verify a number. The worker claims queued jobs atomically; idempotency and uncertain-dispatch handling prevent automatic duplicate calls. Authenticate callbacks and enforce monotonic transitions, callback idempotency and cost caps. Store reported price/inventory separately from recorded offers, with source/timestamps; never update dataset facts or forge seller_confirmed.

The usable demonstration has an explicitly labeled, zero-charge simulation: queued → dialing/sending → waiting → simulated completed/unanswered. These states survive reload and appear in the chat's “پیگیری استعلام” switch. “Return later” is progress guidance, not a promised live ETA. Results always identify simulation or an unverified gateway report. No real call, SMS, payment or production deployment in this task.

## Publish preparation
Create a source release with an allowlist, secret scanning and symlink rejection; exclude `.env*` except `.env.example`, datasets, DB, credentials, logs, browser reference captures and generated build/cache. Preserve the private local configuration outside the release. Include documented server environment variables, DB migrations/import, contact worker, HTTPS callback setup, deployment checks, and Docker/Liara preparation. No deployment, account setup or payment without separate authorization.

## Alternatives and decisions
Use existing Leaflet/OSM for interactive rendering plus server Neshan routing rather than shipping a browser map credential. Use a gateway contract because no call/SMS provider or verified live number was supplied; fabricating a functioning voice bot would be misleading. Use persisted DB jobs rather than background promises tied to an HTTP request so a returning user can retrieve results. User explicitly delegates implementation choices and asks to proceed; the only material UI removal question was answered affirmatively.
